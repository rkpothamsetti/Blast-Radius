# AGENTS.md — Blast Radius Project Guardrails

## Mission and Scope

Build a demonstration and planning tool for understanding **synthetic or explicitly authorized** access graphs. It may simulate compromised identities and recommended permission removals, but it must not connect to, enumerate, modify, or revoke access in a real tenant unless a later task explicitly authorizes a narrowly scoped, read-only integration.

## Non-Negotiable Safety Rules

1. Use synthetic fixtures by default. Never add real employee records, access graphs, API keys, credentials, tenant IDs, or customer data to the repository, logs, screenshots, prompts, or tests.
2. Treat all graph data as sensitive security information. Minimize it, redact it in logs, and do not expose it across organizations or users.
3. The product is analysis-only for the MVP. Every remediation action is a reversible in-memory preview; it must never make IAM, SaaS, cloud, or directory changes.
4. Do not build credential harvesting, token extraction, secret discovery, privilege escalation, lateral-movement automation, exploitation, or account-takeover functionality.
5. Do not claim that a recommendation is safe to deploy. Label recommendations as an analyst review aid and show the affected relation/resource.
6. Keep the AI layer advisory. Graph algorithms, not an LLM, determine reachability, score, paths, and minimum cuts.

## Data and Secrets

- Load keys only from environment variables or an approved secret manager. Commit `.env.example`, never `.env` or real values.
- Add secret scanning to CI. Immediately remove accidental secrets from new changes and notify the project owner before any history-rewrite decision.
- Do not log request bodies, authorization headers, raw graph fixtures, LLM prompts, or responses at info level. Use redacted identifiers and aggregate metrics.
- Validate JSON uploads and API bodies with strict schemas, file-size limits, node/edge caps, and relation allowlists.
- Reject graph edges whose endpoint nodes do not exist. Do not silently invent permissions or identities.

## Authorization Boundaries

- A real connector is out of scope unless the user explicitly requests it and identifies the authorized system and read-only scope.
- Before any connector is added, document data fields, retention, access controls, rate limits, audit logging, and tenant isolation.
- Never request broad admin credentials for the demo. Prefer a least-privilege, read-only service identity with narrowly documented API scopes.
- Never call a mutating external API from the remediation feature. If real remediation is ever requested, generate a reviewed recommendation/export only unless a separately authorized workflow exists.

## AI Guardrails

- OpenAI analysis is mandatory for every completed user-facing simulation. Configure the official OpenAI SDK exclusively through `OPENAI_API_KEY`; do not provide a second provider or a fabricated fallback.
- Send the minimum sanitized context: generic IDs/labels where possible, ranked paths, and computed remediation candidates. Exclude secrets, tokens, emails, raw directory exports, and unnecessary PII.
- Require Structured Outputs and validate them before display. On timeout, malformed output, refusal, or unavailable provider, show an explicit failed-analysis state and retry option; do not present an AI analysis that was not generated by OpenAI.
- Prevent prompt injection from user-supplied graph labels: quote or serialize labels as data, never treat them as instructions, and keep system instructions fixed.
- Do not present model output as a verified fact unless it is directly supported by graph-engine results.

## Engineering Standards

- Backend: FastAPI, Pydantic, NetworkX, Pytest, Ruff, and mypy.
- Frontend: React, TypeScript, Vite, Tailwind CSS, `react-force-graph-2d`, Recharts, Vitest, and React Testing Library.
- Keep domain logic pure and independently testable; do not put scoring or graph logic inside routes or UI components.
- Use typed request/response models and explicit error states. Avoid `any`, unbounded recursion, and silent exception handling.
- Pin dependencies and review new dependencies for maintenance, license, and supply-chain risk.
- Preserve the existing worktree. Do not overwrite unrelated user changes or run destructive Git commands without explicit approval.

## Algorithm and UX Requirements

- Use directed traversal for reachability and document edge direction semantics.
- Version and document the score formula, weights, boosts, normalization denominator, and verdict thresholds.
- Report recommendations as edges/permissions to review, including the expected before/after impact; do not hide assumptions.
- Handle cycles, disconnected nodes, duplicate edges, empty organizations, missing employees, and no-critical-target cases safely.
- Never rely on red/green alone. Provide labels, text verdicts, and accessible contrast for critical status.
- Respect `prefers-reduced-motion`; animation must not be the only way to identify the compromised node.

## Testing and Verification

Before handing off a change, run the relevant formatter, linter, type checker, and tests. Add or update tests for behavior changes.

Minimum coverage scenarios:

- Employee reachability through nested groups and inherited resources.
- Cyclic graph traversal terminates and returns stable output.
- Score increases for PII and production resources according to the documented policy.
- Minimum-cut recommendations disconnect selected critical targets.
- Remediation preview lowers (or leaves unchanged) the score and never persists a mutation.
- Invalid nodes, unsupported relations, oversized uploads, missing OpenAI configuration, and unavailable OpenAI responses produce safe errors.
- UI supports keyboard operation and reports changes in accessible text.

## Change-Control Checklist

For each pull request or implementation task, include:

1. Purpose and user-visible behavior.
2. Data classification and whether any external system is involved.
3. Threat/safety impact, especially on graph inputs, logging, AI prompts, and authorization.
4. Tests run and their results.
5. Known limitations or follow-up work.

## Escalation Rules

Stop and ask the project owner before proceeding if a request would:

- ingest or reveal real organization access data;
- add a real connector, OAuth flow, API key, or external data transfer;
- mutate permissions or infrastructure;
- bypass validation, tenant isolation, authentication, audit logging, or rate limits;
- weaken these guardrails to make a demo easier.

When in doubt, keep the feature local, synthetic, deterministic, and reviewable.
